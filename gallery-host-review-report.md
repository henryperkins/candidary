# Candidary host gallery review

## 1. Verdict

Candidary’s Gallery is mechanically careful but not yet simple enough for the low-frequency, phone-first host in this review. The three modes separate jobs, Library is reassuringly private by default, album edits autosave, and pick/remove copy repeatedly protects the delivered original. But the product asks the host to decode three meanings of “share,” hides audience states until their modes are opened, and gives its most permanent action—the Intake trash button—the least consequence copy. Two boundary defects are worse than terminology: after any completed export the UI cannot prepare a fresh snapshot, and rapid blocked navigation can strand the requested route. Album preview also promises the guest view while omitting its cover, undo can vanish on navigation, and cross-kind export locks are unexplained. At 390px the hierarchy and controls are sound; at 320px the Manager labels collide. Overall: followable after careful reading, not reliably guess-free one-handed a week later. (`src/features/gallery/ManagerGalleryWorkspace.tsx:35-44`, `src/pages/ManagerPage.tsx:799-832`, `src/features/gallery/AlbumExportControl.tsx:76-135`)

## 4. Findings

### S1 — blocked, lost, or irreversible

1. **[VERIFIED] Deleting a guest original has no proportionate guard.** The host is cleaning up Intake → taps an icon-only trash control → the source immediately disappears from Intake and every readable Gallery/album projection → this fails because the most permanent, cross-surface action gives less pre- and post-consequence information than reversible Hide or Remove. The stated rationale is that Gallery should not become a deletion surface and Intake owns original-file actions; that ownership is sound, but it does not justify a one-tap irreversible control for a host afraid of destroying guest photos (`src/features/gallery/ManagerSharedGallery.tsx:77-81`, `src/pages/ManagerPage.tsx:679-684`, `src/pages/ManagerPage.tsx:799-832`, `tests/worker/album-api.test.ts:329-350`, `tests/worker/album-share-api.test.ts:458-492`). **Specific fix:** keep deletion in Intake, but make the first tap open a focused confirmation region that says: `Permanently delete this guest’s original? It will disappear from Library, the album, the optional gallery, and any live album link. This cannot be undone.` Actions: `Keep photo` and danger `Delete original`. On success, focus the next card (or Intake heading if none) and announce `{title} was permanently deleted.`

2. **[VERIFIED] A terminal export hides the current-export action.** The host delivers or picks more photos after an export → opens the corresponding download card → sees only the old Ready/Failed/Expired job and its links/retry → cannot prepare a snapshot containing the current collection/album while that retained job owns the card. This fails the workflow, and `Retry export` reinforces the wrong belief that retry means “try the current set.” The component rationale keeps all states in “that same logical job”; the immutable-snapshot contract makes that correct for retry, but the UI also needs a new-job path (`src/features/gallery/GalleryExportControl.tsx:55-59`, `src/features/gallery/GalleryExportControl.tsx:90-145`, `src/features/gallery/AlbumExportControl.tsx:76-135`, `docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:212-224`). **Specific fix:** on every terminal card show `Prepared {date} · {n} photos`; retain links and rename retry `Retry this prepared export`; below it add `Prepare current collection` in Library or `Prepare current album` in Album. While a job is queued/running, do not show the new-prepare action. This intentionally revises the single-action/same-job rule and exact Album export contract, so edit `docs/superpowers/specs/2026-08-13-host-private-gallery-design.md:128-145,457-461` and `docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:208-234` with the UI change.

3. **[INFERRED] A second blocked route can remain blocked behind the first route’s preparation.** The host presses Back, then a second destination while Album is settling → the Router changes `blocker.location.key`, but the preparation effect does not rerun → the first result no longer matches and the latest destination receives no fresh result. This fails because the host’s latest explicit route can silently stall (`src/pages/ManagerPage.tsx:263-298`). **Specific fix:** implement the already-written remediation: key the effect by `blockedNavigationKey`, increment the generation for each key, and call `proceed()` only when both the generation and result `navigationKey` match; add the two-destination regression described at `docs/superpowers/plans/2026-08-23-pr-33-review-remediation-release.md:450-477`.

4. **[INFERRED] A failed Album save can leave no way to discard and leave.** The host is offline or a save remains failed → selects another Gallery mode/Manager section and simply remains in Album with recovery focused, or uses a client route and sees disabled `Leave now` → can only retry the condition that is already stuck. This fails because navigation is indefinitely unavailable even though the route prompt says unsent work can be discarded. The binding rationale deliberately makes `prepareToLeave()` return false so conditional unmount cannot dispose a scheduled draft, and the prompt correctly refuses to promise recall of a sent request; retain both protections (`src/features/gallery/ManagerAlbum.tsx:825-890`, `src/features/gallery/ManagerGalleryWorkspace.tsx:152-190`, `src/pages/ManagerPage.tsx:629-645`, `src/pages/ManagerPage.tsx:1177-1195`, `src/components/UnsavedSettingsPrompt.tsx:33-50`, `docs/superpowers/plans/2026-08-23-album-workspace-end-to-end.md:456-460`). **Specific fix:** add one explicit `Discard unsent Album changes and leave` decision only after failed/invalid preparation. Wire it through a workspace discard handle for mode switches, section switches, and Router blockers; discard unsent queue state, preserve `A change already sent may still finish saving after you leave.`, then take the requested destination. During temporary settling, keep Leave disabled and show `Finishing Album checks before Leave now is available.` This requires coordinated contract edits to the leave rule at `docs/superpowers/plans/2026-08-23-album-workspace-end-to-end.md:456-460` and remediation Task 5 at `docs/superpowers/plans/2026-08-23-pr-33-review-remediation-release.md:450-485`.

5. **[VERIFIED] Stopping a link irreversibly invalidates its URL without warning.** The host sees the active URL → taps `Stop sharing album` → the credential disappears immediately and the old URL/sessions fail on the next request. `[INFERRED]` A page already rendered can retain photos that loaded before Stop while later lazy preview requests fail. This is S1 because issuing a later link cannot restore the URL the host already distributed (`src/features/gallery/ManagerAlbum.tsx:1275-1287`, `src/features/gallery/ManagerAlbum.tsx:1642-1675`, `src/pages/AlbumSharePage.tsx:45-90`, `src/features/gallery/PublicAlbum.tsx:27-33`, `src/features/gallery/PublicAlbum.tsx:85-90`, `worker/services/album-share.ts:122-188`). **Specific fix:** preserve the exact `Stop sharing album` control, then show: `Stop sharing this album? The current link will stop working immediately. People who already have it open may still see photos that have already loaded. Sharing again creates a new link.` Actions: `Keep sharing` and danger `Stop sharing album`. After success announce `Album link stopped. The old link no longer works.` Update the approved share contract alongside it at `docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:180-189`.

The workspace comment deliberately treats the count as decoration and preserves the last good number on read failure, but this host reads a visible number as current state, so silent staleness costs trust (`src/features/gallery/ManagerGalleryWorkspace.tsx:116-126`, `src/features/gallery/ManagerPrivateGallery.tsx:705-714`, `src/features/gallery/ManagerAlbum.tsx:1306-1385`, `src/features/gallery/GalleryExportControl.tsx:36-45`, `src/features/gallery/AlbumExportControl.tsx:28-35`). **Specific fix:** have `ManagerAlbum` report its current trusted photo/entry counts to the workspace after canonical adoption or confirmed membership writes; use that one value for both visible labels. If neither that report nor a fresh read is trusted, suppress the parenthetical instead of showing the last good number. Label export counts `Prepared {date} · {n} photos` so an intentional snapshot difference cannot look like disagreement.

18. **[VERIFIED] Remove uses a completion checkmark.** The host selects photos → sees a Plus for Add and a Check for `Remove {n} from album` → the glyph implies already selected/completed rather than subtracting. ## 5. Explicit answers to the seven questions

1. **Are three modes the right decomposition?** Yes. Library owns the private source and picking, Album owns one curated artifact, and Shared owns event-guest publication; moving Shared back to Intake would reunite permanent source actions with public visibility and make the three-card problem worse. The wrong part is not placement but naming and state orientation: `Shared` does not identify the optional guest gallery, while its on/off setting is several steps away (`docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:13-30`, `src/features/gallery/ManagerSharedGallery.tsx:125-148`). Keep three modes; rename the internal mode and expose one shared state sentence.

2. **Does a host who skips mode notes learn picking vs publishing vs sharing?** Not reliably. They first learn picking from an `In album` badge/action, publication from Publish/Hide inside Shared, and link sharing only after reaching `Share album`; those controls work, but the distinction emerges through experiment across three screens. The strongest explanation—`Publication is a separate axis from the album`—arrives only after Shared is chosen (`src/features/gallery/GalleryMoment.tsx:93-114`, `src/features/gallery/ManagerSharedGallery.tsx:125-128`, `src/features/gallery/ManagerAlbum.tsx:1642-1669`). The cost is one wrong mental model before the explanation, especially because `Share`, `Shared`, and `Share album` all remain visible product words.

3. **Is guest-photo deletion proportionate and in the right place?** It is in the right ownership surface: Intake already owns the original download, while Gallery intentionally avoids arbitrary asset management. It is not guarded in proportion to permanence. One icon tap can remove the source from all visible projections without consequence copy, confirmation, undo, success sentence, or stable focus (`src/pages/ManagerPage.tsx:799-832`, `src/features/gallery/ManagerSharedGallery.tsx:77-81`). Keep the action in Intake and add the focused, cross-surface permanent-delete confirmation and post-delete focus/announcement specified in S1.1.

4. **Do the exports present one mental model, and should they?** They present one good state vocabulary—Preparing, Ready, Failed, Expired, Get links, Retry—but two correctly different scopes. They should remain two entry points because `Download all` includes every original and Guestbook artifacts while Album export follows current album membership/order and excludes Guestbook (`src/features/gallery/GalleryExportControl.tsx:34-45`, `src/features/gallery/AlbumExportControl.tsx:28-35`, `src/features/gallery/AlbumExportControl.tsx:76-90`). They should share one snapshot model, collision explanation, and current-snapshot action; scope should differ, lifecycle should not.

5. **Can the host tell at a glance what guests and link-holders see?** No. Optional-gallery on/off appears only after opening Shared; album-link state is fetched and shown only after opening Album; the mode switch shows only an Album count, and `Published` can coexist with gallery off (`src/features/gallery/ManagerGalleryWorkspace.tsx:197-212`, `src/features/gallery/ManagerAlbum.tsx:704-719`, `src/features/gallery/ManagerSharedGallery.tsx:140-148`). A host must open two modes and retain two audiences in memory. The proposed one-line Gallery state summary is the smallest cross-mode answer.

6. **Can two numbers describe the same thing differently?** Yes under failure/timing: the editor’s local `{n} photos in the album` can advance while the lifted server count fails and silently keeps the old `Album ({n})`/`Album picks ({n})`. Export counts can also differ intentionally because they are frozen, but no date labels that fact (`src/features/gallery/ManagerGalleryWorkspace.tsx:116-126`, `src/features/gallery/ManagerAlbum.tsx:1306-1385`, `src/features/gallery/GalleryExportControl.tsx:36-45`). Report one trusted Album count to both labels, preserve the last known value if refresh fails, and add explicit `Prepared {date}` snapshot labels so legitimate history cannot look like drift.

7. **What is the single highest-cost moment and smallest remedy?** Intake deletion. It combines fear, irreversible source loss, multi-surface consequence, no recovery, and no sentence acknowledging the action. The smallest adequate change is not a redesign: preserve Intake ownership and insert one confirmation region with the exact cross-surface consequence, followed by deterministic focus and `{title} was permanently deleted.` (`src/pages/ManagerPage.tsx:679-684`, `src/pages/ManagerPage.tsx:825-832`). The export dead-end blocks more routine completion, but it cannot destroy the only copy of a guest’s photo.

## 8. Open product questions

1. **A live link after the album becomes empty:** keep the active URL and let it show `0 photos`, preserving URL continuity; or automatically stop/require confirmation on removing the last pick, preventing a blank public artifact but invalidating a URL as a side effect. Current code chooses continuity (`src/features/gallery/ManagerAlbum.tsx:1642-1675`, `src/features/gallery/PublicAlbum.tsx:60-95`).

2. **Single-original retrieval:** keep `Download original` exclusively in Intake, preserving clean Gallery roles but forcing search-oriented hosts to backtrack; or add a labelled original-download exit to Library’s viewer, reducing backtracking but expanding the approved four-action private-gallery boundary (`src/pages/ManagerPage.tsx:819-825`, `docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:34-44`).

3. **Visibility summary versus the above-fold contract:** permit exactly one dynamic Gallery state sentence, making both audiences legible on arrival; or keep the global contract absolute and accept mode-by-mode inspection. The first choice requires the explicit `design/design-system.md:322,370` edit identified in S2.6; adding ungoverned pills/badges is not a third option.

4. **Shared-gallery on/off ownership:** retain the event-level toggle in Settings, keeping Settings as the source of global event behavior but requiring a return-intent bridge; or place the same toggle in Shared, reducing travel but mixing availability with photo-level publication. The current design deliberately chooses Settings (`src/features/gallery/ManagerSharedGallery.tsx:140-148`, `src/components/EventSettingsEditor.tsx:524-541`).

5. **Request-time versus published album revisions:** keep the current request-time projection, so membership/order/cover edits affect the next open/reload while an already open holder page stays as rendered; add polling/push so open pages refresh; or introduce an explicit publish-revision step that freezes a named version. The latter two improve one kind of predictability but add real-time churn or a high-cost commit state (`src/pages/AlbumSharePage.tsx:45-90`, `worker/db/album.ts:100-156`, `docs/superpowers/specs/2026-08-23-album-workspace-end-to-end-design.md:180-206`).

6. **Export history:** show only the latest job plus a “prepare current” action, keeping the surface small; or expose a dated export history, helping audit/retrieval but turning a download control into archive management. Current Manager state deliberately selects only the latest job of each kind (`src/pages/ManagerPage.tsx:556-558`).
